# HERMES_ROUTING — open-tasks (local relay origin · qa merge-gate · no PR · no push-past-upstream)

> This file auto-injects into every agent's context when Hermes works in this
> repo. It defines the **routing + merge** workflow here. Read it before you hand
> off or finish any card. It holds **regardless of who originates the work**; there
> is **no PR-capable remote an agent can reach.**

## Topology — the "origin" is a LOCAL relay, not GitHub
- This workspace is `/Users/tom/Projects/_workspaces/open-tasks`. Its `origin` is a
  **local git clone (the relay)** at `/Users/tom/Projects/origins/open-tasks`.
  That clone's **own** `origin` points at upstream GitHub.
- **Agents only ever reach the local relay.** Nothing is ever pushed past it — no
  GitHub, no external host. The relay is the boundary.
- Integration branches, currently all at the same commit:
  `develop` (agents integrate here) → `staging` → `main` (human/deploy).

## Code/data only lands in `develop` via **qa**. Everyone else routes to qa.
1. **Implementers own the implementation, not the merge.** A code- or data-adding
   role (`junior-eng-1`, `junior-eng-2`, `senior-eng`) implements a `ready` task as
   **one coherent commit on a work branch off `develop`**, then hands it off:
   ```
   hermes kanban request-review <id> --reviewer qa --summary "what changed + how verified + what to look at first"
   ```
   **Do NOT `complete` your own card and never merge or push.** qa is the gate.
2. **qa is the only merge gate into `develop`** (`request-review --reviewer qa`
   routes the card to qa). qa's job:
   1. `git fetch`, then **rebase the task's work branch onto current `develop`** so
      the verify runs against the latest base. (Agents **may rebase their own
      working branches** — this is the one history action agents own.)
   2. **Build / test / verify** every acceptance criterion against the rebased tip.
   3. **Pass** → fast-forward `develop` onto the rebased branch, update the relay,
      then close the card:
      ```
      git merge --ff-only <work-branch> develop   # rebased => fast-forward
      git push origin develop                       # updates the LOCAL relay only
      hermes kanban complete <id>
      ```
      (a rebased merge is `--ff-only`; if it is **not** fast-forward, the base drifted
      — `request-changes` back to the implementer to rebase.)
   4. **Fail** → `hermes kanban request-changes <id> <concrete fix list…>` — the card
      bounces back to the role that owns it, defects named.
3. **No agent merges into `staging` or `main`, and nothing is pushed past the local
   relay.** The `develop → staging → main` promotions, and any upstream rebase or
   history rewrite, are **human-only** (fast-forward promotions; history may be
   rewritten by a human). **Nothing is ever pushed from an agent beyond `origin`
   (the relay).**

## Remote-agnostic guardrails (also true here for the no-PR case)
- There is **no PR** to open — the relay has no PR flow an agent can use, and
  upstream GitHub is not reachable. **qa merge-to-`develop` is the whole review
  signal.** Do not attempt a PR or `git merge` on your own.
- If you ever need to reference a branch on the relay, `git push origin <branch>`
  is the **local relay only** — that is the outer boundary.

## One task = one coherent commit
Commit only when the change works (tests/build pass; manual check where no test is
feasible). Do not `complete` before qa has fast-forwarded it into `develop`.

## Branching
- Cut work branches from **`origin`/`develop`** (`origin/HEAD` = `develop`). Never
  branch off `main`/`staging`, and never push `main`/`staging`.
- Prefer **small, independently reviewable** commits so qa can verify each in isolation.

## Deviation to reconcile with the repo's own design
- open-tasks design **ADR-0020 ("Pull Requests as Review Authority")** assumes a
  PR-capable remote. This board instead routes through **qa's verify + fast-forward
  merge to `develop`** (team operating model D13) as the review authority. Treat
  "review" as *qa-merge-to-develop*, not a GitHub PR. Flag this mismatch in the
  next planning meeting; do not silently follow ADR-0020 here.
